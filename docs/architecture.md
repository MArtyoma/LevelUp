# Как устроена игра

*Документ для тех, кто пишет код: лид и artist. Обновляется вместе с кодом.*

## Одно решение, из которого следует всё остальное

**В коде нет содержания игры.** Ни одного имени сотрудника, ни одной реплики, ни одного
квеста. Всё это лежит в `data/*.json`; код — это оболочка, которая умеет показать *любую*
компанию.

Решение записано как D-003 и D-013 в реестре решений (репозиторий документации). Принималось
оно ради персональных данных заказчика, но оказалось важнее: из него следует почти вся
остальная архитектура.

| Следствие | Что это даёт проекту |
|---|---|
| writer пишет легенду и диалоги в JSON | человек без опыта разработки производит содержание игры, не открывая редактор кода |
| level designer ставит NPC и вписывает `employee_id` | левел-дизайн без единой строки кода |
| Данные проверяются скриптом | ошибка ловится за 5 секунд в CI, а не за неделю до защиты на плейтесте |
| Подмена папки данных — другая компания | реальные ФИО заказчика никогда не попадают в репозиторий |
| Игра одинаково стартует у всех участников замера | иначе на неделе 9 нечем объяснить разброс цифр |

## Слои

```
        данные                 состояние              представление
   ┌───────────────┐      ┌─────────────────┐     ┌──────────────────┐
   │   GameData    │      │    QuestLog     │     │    GameUi        │
   │  company.json │      │ DialogueRunner  │     │   DialogueBox    │
   │ dialogues.json│      │   Telemetry     │     │  Player, Npc     │
   │  quests.json  │      │    SaveGame     │     │   AccessDoor     │
   └───────┬───────┘      └────────┬────────┘     └─────────┬────────┘
           │  читают                │  сигналы              │
           └────────────────────────┴───────────────────────┘
                              EventBus

                     Grid ──────────────► все размеры
              (levelup/grid в настройках проекта)
```

Правило, на котором всё держится: **вниз — вызовы, вверх — сигналы.** Представление читает
данные и состояние напрямую, но менять их может только через методы; состояние о представлении
не знает вообще и кричит в `EventBus`.

Что это даёт практически: панель квестов можно переписать с нуля, не открывая ни одного файла
с игровой логикой, и наоборот. Код пишут двое — граница между ними проходит ровно по `EventBus`.

## Автозагрузки: почему именно эти шесть с половиной

Автозагрузка — глобальный объект, и их легко развести десяток, после чего в проекте не остаётся
ни одного места, о котором можно сказать «состояние живёт здесь». Поэтому список закрыт, и каждая
позиция в нём отвечает на вопрос «что сломается, если её не будет».

* **EventBus** — без него системы начнут держать ссылки друг на друга.
* **GameData** — данные читаются один раз; иначе каждая реплика лезла бы в файл.
* **QuestLog** — единственное место состояния прохождения.
* **DialogueRunner** — разговор идёт поверх любой сцены и переживает переходы.
* **Telemetry** — подписана на всё сразу, ничего не зная о подписчиках.
* **Sound** — музыка не должна обрываться при смене сцены, а звук события — зависеть
  от того, какая сцена открыта. Как Telemetry, слушает шину и никому о себе не говорит;
  напрямую её зовут только окно разговора (щелчки вариантов) и игрок (шаги) — на такие
  мелочи сигналов в шине нет и не будет.
* **SaveGame** — тонкая обёртка над QuestLog, отдельная только потому, что формат файла
  меняется чаще, чем состояние.

Новая автозагрузка добавляется через разговор с лидом, а не молча.

## Что сделано ради скорости

Игра маленькая, и «оптимизация» здесь — это не микросекунды, а решения, которые не дают
проекту деградировать по мере роста.

1. **Рендер — `gl_compatibility`.** Игра запускается на слабых ноутбуках и встроенной графике,
   а именно на них будет проходить замер на неделе 9. Vulkan там местами просто не стартует.
2. **Маленькое окно, растяжение `canvas_items` + целочисленный масштаб.** Мир рисуется в родном
   разрешении (по умолчанию 480×272 — это 30×17 тайлов) и увеличивается целым числом раз.
   Никакого зума камеры: дробный зум даёт дрожащие пиксели, которые невозможно «починить» потом.
3. **Спящие узлы.** У NPC, дверей и предметов `_process` и `_physics_process` выключены. Они
   реагируют на события, а не опрашивают мир каждый кадр. Двенадцать спящих NPC вместо
   двенадцати работающих — мелочь; тридцать таких мелочей — уже разница.
4. **Поиск по словарю, а не по списку.** `GameData` строит индексы один раз при загрузке.
   Диалог дёргает `get_employee()` на каждой реплике — там перебор массива недопустим.
5. **Взаимодействие через физику, а не через перебор.** Игрок не считает расстояние до всех
   NPC каждый кадр: список «до кого можно дотянуться» наполняет сигналами `Area2D`, и он почти
   всегда пуст.
6. **Таймер дуэли включается только на время дуэли** (`set_process(true/false)`).
7. **Один спрайт человека на всех**, цвет — из данных через `modulate`. Пятнадцать сотрудников
   без пятнадцати рисунков; для команды с двумя-тремя художественными часами в неделю это
   не украшение, а условие выживания.

## Размеры: одно число вместо двадцати

Размер тайла — параметр, который в обычном проекте расползается по коду двумя десятками
чисел: коробка столкновений игрока, радиус, с которого он дотягивается до NPC, смещение
спрайта, положение подписи над головой, размер окна, регион в атласе, скорость ходьбы.
Поменять 16 на 32 означает найти их все, и одно обязательно потеряется — а проявится через
неделю как «игрок почему-то проходит сквозь угол стола».

Поэтому в проекте **нет ни одного размера в пикселях, кроме одного**. Всё остальное —
доли тайла, собранные в `src/core/grid.gd`.

Настройки лежат там, где их увидит любой участник без кода:
**Проект → Настройки проекта → Основные → `levelup/grid`.**

| Настройка | Что задаёт |
|---|---|
| `tile_size` | размер тайла в пикселях: 16, 32, 64 |
| `character_frame_width/height` | кадр в спрайт-листе человека. 16×32 означает, что голова торчит над линией тайла |
| `walk_frames` | кадров в цикле ходьбы |
| `visible_tiles_x/y` | сколько тайлов помещается на экран |

Два обещания, которые держит `Grid` и проверяют тесты (`tests/test_grid.gd`):

* **на экран всегда влезает одно и то же число тайлов** — игрок видит одинаковый кусок офиса
  и при 16, и при 64;
* **скорость задана в тайлах в секунду, а не в пикселях** — прохождение занимает те же
  15–20 минут. Это не удобство, а условие эксперимента: контрольная группа ровно столько же
  смотрит презентацию.

### Как поменять размер

```bash
# 1. Настройки проекта -> levelup/grid/tile_size -> 32
# 2. Перерисовать атлас тайлов и общий спрайт человека под новый размер
python3 tools/art/draw_tiles.py
python3 tools/make_placeholder_art.py
# 3. Пересобрать тайлсет (коробки столкновений заданы долями тайла)
godot --headless --script tools/build_tileset.gd
# 4. Только если карта уже собрана руками - пересчитать позиции на ней
godot --headless --script tools/rescale_level.gd -- --from=16 --to=32
```

Четвёртый шаг нужен потому, что сами тайлы хранятся клетками и перерисуются сами, а NPC
и двери стоят по пикселям. **Коммит перед четвёртым шагом обязателен:** скрипт правит сцену
на месте.

Интерфейс масштабируется вместе с окном (`Grid.ui_scale`), иначе на тайле 64 подписи
превращаются в муравьёв в углу экрана.

## Кто кого закрывает на экране

Мир рисуется **по Y**: кто ниже на экране, тот поверх. Так персонаж 16×32 перед столом
закрывает стол головой, а за столом — прячет за ним ноги. Для этого сортировку по Y
включают у корня уровня, у слоя `Walls` (стены и мебель, каждый тайл сортируется
отдельно) и у людей.

* **`z_index` в мире не ставим.** Исключения два, оба осознанные: пол (`Ground`) — `-1`,
  всегда под всем; подпись с именем над NPC — `1`, всегда над всем. Раньше у `Walls`
  стоял `z_index = 1`, и вся мебель рисовалась поверх людей, где бы они ни стояли.
* **Стену «лицом» рисует скрипт** `src/levels/wall_faces.gd`: при запуске уровня каждая
  стена, под которой пол, меняется на тайл-лицо (6,1). level designer рисует карту одним тайлом стены.
* **Своя картинка сотрудника** ищется по его id (`src/core/own_art.gd`):
  `assets/sprites/npc/<id>.png`, потом `<id>_placeholder.png`, иначе общий спрайт
  с цветом `palette` из данных. Портрет в окне разговора — так же, в `assets/portraits/`.

## Звук

`src/autoload/sound.gd` слушает шину и играет звук на событие. Какой звук на какое
событие — в самом файле (`_connect_to_bus`), громкость каждого — там же (`VOLUME_DB`),
общая громкость музыки и звуков — шины `Music` и `SFX` в `default_bus_layout.tres`.

* **Файлы — по имени, как картинки:** `assets/sfx/<имя>.wav` важнее
  `<имя>_placeholder.wav`; варианты `<имя>_0`, `<имя>_1`… играются вперемешку (шаги).
  Музыка — `assets/music/<имя>.ogg`, петля включается кодом. Нет файла — тишина.
* **Голос собеседника** — один писк на реплику, высота из id сотрудника: у каждого свой
  и всегда один и тот же.
* **Шаг звучит по поверхности:** у тайлов пола в тайлсете есть слой данных `surface`
  (`carpet`, `tile`; задаётся в `tools/build_tileset.gd`). Новый пол — новая строка
  там и файлы `step_<surface>_N.wav`.
* **Дуэль переключает музыку** на `duel` и после разговора возвращает прежнюю.
* **Несколько событий за кадр — один звук**, самый важный: последняя цель квеста,
  закрытие квеста и новый пропуск звучат как «квест выполнен», а не тремя сразу.
* **M** выключает весь звук. В headless (тесты, CI) звуки не играют, только
  записываются в `Sound.recent`: так тесты проверяют, что прозвучало.

Их же гоняет GitHub на каждый push и pull request.

| `tests/test_quest_log.gd` | шаги квестов закрываются по порядку, условие `step` следует порядку, пропуск не понижается, состояние переживает сохранение |
| `tests/test_dialogue_runner.gd` | диалоги, условия на вариантах ответа, выигранная и проигранная дуэль, сквозное прохождение |
| `tests/test_dialogue_box.gd` | окно разговора с клавиатуры: на любых вариантах есть выделенный, E выбирает его |
| `tests/test_sound.gd` | у каждого звука есть файл; голос сотрудника постоянный; три события за кадр дают один звук; музыка дуэли включается и выключается; шаги различают ковролин и плитку |
| `tests/test_save_game.gd` | настоящий файл на диске; повреждённое и чужое сохранение не роняют игру |
| `tests/test_grid.gd` | проект переживает смену размера тайла на 16, 32 и 64 |
| `tests/test_level_scene.gd` | **карта сходится с данными и игра проходима до конца**; до каждого сотрудника и предмета можно дойти — мебель не перегородила проход |

Последний — самый ценный. Он читает `office_demo.tscn` как данные и проверяет стык, на котором
игра ломается чаще всего: NPC ссылается на существующего сотрудника, у каждого есть что сказать,
закрытая дверь в принципе открывается доступным пропуском, а каждый шаг каждого квеста
закрывается либо репликой в диалоге, либо предметом на карте. Если writer переименует сотрудника,
а level designer об этом не узнает — красный крестик появится через три минуты, а не через две недели
на плейтесте.

## Чего здесь сознательно нет

Записано, чтобы не пришлось объяснять это заново на пятой неделе.

* **Нет ECS и нет менеджера менеджеров.** Объём v1 — один этаж, 12 NPC, 5 квестов. Архитектура
  под миллион сущностей стоила бы больше, чем сама игра.
* **Нет графа зависимостей между шагами квеста.** Шаги идут по порядку. Когда понадобится
  ветвление — добавим, а пока это лишняя сложность в том месте, где тексты пишет новичок.
* **Нет собственного формата данных и нет редактора данных.** JSON правится блокнотом,
  ошибки ловит валидатор. Админка вынесена за границы v1 уставом.
* **Нет сетевого кода, сохранения в облако, достижений.** См. «Не входит в v1» в уставе.
