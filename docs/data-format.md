# Как заполнять данные игры

*Этот документ для writer — он владелец папки `data/`. Кода знать не нужно.*

В `data/` три файла. Всё, что в них написано, игрок увидит в игре; всё, чего там нет, в игре
не существует. Файлы — обычный текст, правятся блокнотом или любым редактором.

**Проверить себя после правки — одна команда:**

```
godot --headless --script tools/validate_data.gd
```

Она печатает по-русски, что не так и в какой строке. Ошибок нет — можно коммитить.
Если Godot под рукой нет, просто сделайте push: то же самое проверит GitHub и напишет в
pull request.

**Правило про запятые.** В JSON после последнего элемента списка запятая не ставится, а между
элементами — ставится. Девять ошибок из десяти — про это. Проверка скажет номер строки.

## 1. `company.json` — кто в компании работает

```json
{
  "company": { "id": "meridian", "name": "«Меридиан»", "field": "чем занимается", "legend": "два абзаца о компании" },

  "departments": [
    { "id": "dept_hr", "name": "Отдел кадров", "head": "emp_mironova", "room": "room_hr",
      "purpose": "Оформление, пропуска, отпуска." }
  ],

  "employees": [
    { "id": "emp_mironova", "name": "Елена Миронова", "role": "руководитель отдела кадров",
      "department": "dept_hr", "reports_to": "emp_koroleva", "palette": "#68d391" }
  ],

  "topics": [
    { "id": "topic_vacation", "title": "отпуск",
      "question": "К кому идти, чтобы оформить отпуск?", "owner": "emp_mironova" }
  ]
}
```

| Поле | Что писать |
|---|---|
| `id` | латиницей, без пробелов, уникально. Это внутреннее имя, игрок его не видит |
| `name`, `role` | как увидит игрок. Должность — с маленькой буквы: она дописывается к имени |
| `department` | `id` отдела, в котором человек работает |
| `reports_to` | `id` его начальника. У генерального директора — пустая строка |
| `head` у отдела | `id` руководителя. Он обязан работать в этом же отделе |
| `palette` | цвет рубашки на карте, вида `#68d391`. Разные отделы — разные цвета |

### `topics` — самое важное поле во всём проекте

Темы — это то, **из чего собирается тест для проверки гипотезы** (неделя 9). Каждая тема даёт
один вопрос теста, а `owner` — единственный правильный ответ на него.

Отсюда три требования, и проверка ругается на нарушение каждого:

1. **У темы ровно один владелец.** Если «согласовать бюджет» может и финансовый директор,
   и руководитель отдела — в тесте у вопроса два правильных ответа, и замер меряет шум.
2. **Двух одинаковых вопросов не бывает.**
3. **Каждый отдел отвечает хотя бы за одну тему.** Отдел, которого нет в тесте, — декорация:
   он не работает на гипотезу.

Тем нужно **не меньше десяти** — по числу вопросов теста.

## 2. `quests.json` — что игрок делает

```json
{
  "quests": [
    {
      "id": "q_onboarding",
      "title": "Оформиться в компании",
      "giver": "emp_mironova",
      "summary": "Одна строка — о чём это задание.",
      "objectives": [
        { "id": "obj_docs",   "text": "Забрать папку с документами в отделе кадров" },
        { "id": "obj_laptop", "text": "Зайти к Артёму Киму за ноутбуком" }
      ],
      "reward": { "access_level": 2 },
      "teaches": ["topic_pass", "topic_vacation"]
    }
  ]
}
```

* **`objectives` закрываются по порядку**, сверху вниз. Второй шаг не засчитается, пока не
  закрыт первый.
* **`text` шага — это то, что игрок читает в журнале.** Он должен отвечать на вопрос «что мне
  сейчас делать», а не описывать сюжет. «Зайти к Артёму Киму за ноутбуком» — годится.
  «Продолжить оформление» — нет.
* **`reward.access_level`** — новый уровень пропуска. Так открываются закрытые кабинеты.
* **`teaches`** — список тем, которые этот квест объясняет игроку. Проверка сверяет: всё, что
  спрашивается в тесте, игра должна где-то показать. Иначе мы спросим то, чего не показали,
  и результат замера будет нечестным.

## 3. `dialogues.json` — что говорят

Разговор — это набор реплик, каждая со своим именем. Из реплики можно уйти в следующую (`next`)
или предложить игроку выбор (`choices`). Слово `"end"` заканчивает разговор.

```json
{
  "dialogues": [
    {
      "id": "dlg_mironova",
      "speaker": "emp_mironova",
      "start": "greet",
      "teaches": ["topic_vacation"],
      "nodes": {
        "greet": { "text": "Так, новенький. Пропуск и отпуск — это ко мне.", "next": "offer" },
        "offer": {
          "text": "Забери папку со стола и сходи к Артёму за ноутбуком.",
          "choices": [
            { "text": "Понял, иду.", "next": "bye",
              "effects": [ { "type": "start_quest", "quest": "q_onboarding" } ] },
            { "text": "А где ИТ-отдел?", "next": "where_it" }
          ]
        },
        "where_it": { "text": "По коридору направо.", "next": "offer" },
        "bye": { "text": "Заходи, если что.", "next": "end" }
      }
    }
  ]
}
```

### Действия — `effects`

Ставятся либо на реплику (сработают, когда её покажут), либо на вариант ответа (сработают,
когда игрок его выберет).

| Действие | Запись | Что делает |
|---|---|---|
| выдать квест | `{ "type": "start_quest", "quest": "q_onboarding" }` | задание появляется в журнале |
| закрыть шаг | `{ "type": "complete_objective", "quest": "q_onboarding", "objective": "obj_laptop" }` | отмечает шаг выполненным |
| поднять пропуск | `{ "type": "grant_access", "level": 2 }` | открывает закрытые кабинеты |
| поставить отметку | `{ "type": "set_flag", "flag": "представился" }` | запомнить, что что-то уже было |
| закончить игру | `{ "type": "finish_game" }` | финал прохождения |

### Условия — `requires`

Показывать вариант ответа не всегда. Пишется у варианта; все перечисленные условия должны
выполняться одновременно.

```json
{ "text": "Меня прислала Елена за ноутбуком.", "next": "give",
  "requires": { "quest_active": "q_onboarding" } }
```

| Условие | Смысл |
|---|---|
| `"flag": "имя"` | отметка поставлена |
| `"not_flag": "имя"` | отметка не поставлена |
| `"quest_active": "q_..."` | квест взят и не закончен |
| `"quest_done": "q_..."` | квест закончен |
| `"access": 2` | пропуск не ниже второго уровня |

Вариант, не прошедший условие, **не показывается вовсе** — не серым, а отсутствует. Так игрок
не видит подсказку о том, чего ещё не знает: иначе он угадает ответ теста, не пройдя игру.

### Дуэль согласования

Особый вид разговора (решение D-002): руководитель кидает возражения, у игрока ограниченное
время и запас терпения собеседника.

```json
{
  "id": "dlg_pavlov",
  "speaker": "emp_pavlov",
  "kind": "duel",
  "patience": 3,
  "time_limit": 10.0,
  "on_wrong": "again",
  "start": "challenge",
  "nodes": {
    "challenge": {
      "text": "Клиент просит скидку сверх регламента. Твои действия?",
      "choices": [
        { "text": "Согласую с вами.", "correct": true, "next": "ok" },
        { "text": "Дам скидку." }
      ]
    },
    "again": { "text": "Мимо. Ещё раз: кто отвечает за условия договора?", "choices": [ ] },
    "ok":    { "text": "Годится.", "next": "end" }
  }
}
```

* `patience` — сколько промахов выдержит собеседник.
* `time_limit` — секунд на ответ. Промолчал — считается неверным ответом.
* `on_wrong` — куда уходит разговор после промаха. Обычно это повтор вопроса другими словами.
* Хотя бы один ответ обязан быть помечен `"correct": true`.

## Как писать тексты, чтобы игра работала на гипотезу

Игра проверяет одно: запоминает ли человек **структуру компании** — кто за что отвечает и к
кому идти с чем. Всё, что этому не помогает, — украшение.

* **В каждом разговоре должно быть видно, за что человек отвечает и где проходит граница
  его ответственности.** «Техника — ко мне, не к Дмитрию» — одна фраза, и она учит.
* **Говорите про чужие отделы.** Игрок запоминает связи, а не список. «Счёт визирует
  руководитель отдела, который его заказал, потом он идёт ко мне» — это и есть содержание игры.
* **Реплика — две-три строки.** Всё прохождение должно укладываться в 10–15 минут:
  контрольная группа столько же смотрит презентацию, иначе сравнивать нечего.
* **Никаких реальных ФИО и названий компаний.** Компания в v1 вымышленная (D-005), и это
  не ограничение, а более чистая методика: стартовое знание у всех участников замера ровно
  нулевое.
